@AGENTS.md

## Commands

- `npm run dev` — start the dev server (Turbopack) at http://localhost:3000
- `npm run build` — production build; this also type-checks the project (`next build` runs `tsc` as part of the build)
- `npm run start` — serve the production build
- `npm run lint` — ESLint (flat config: `eslint-config-next` core-web-vitals + typescript)

There is no test suite configured in this repo.

## Cloudflare

- Deployed to Cloudflare Workers as a **static site** (`wrangler.jsonc`, `assets.directory: ./out`). `npm run build:cloudflare` sets `NEXT_OUTPUT=export`, which switches `next.config.ts` from `output: "standalone"` to `output: "export"` and writes one HTML file per route to `out/`. `wrangler.jsonc` runs that command itself (`build.command`) before `wrangler deploy` / `wrangler preview`, and has the empty `previews` block that `wrangler preview` requires.
- This only works because every route is static and all data is fetched from the backend by the browser (`NEXT_PUBLIC_API_URL` must be set when building, e.g. in `.env.production`). Adding server features (route handlers that read the request, middleware/proxy, `cookies()`/`headers()`, `next/image` optimization) would break the static export — the deploy would then need the OpenNext Cloudflare adapter instead.

## Docker

- `NEXT_PUBLIC_API_URL` is inlined at build time, so the `Dockerfile` takes it as a build arg and `docker-compose.yml` requires it (from the shell or a `.env` next to it — `.env*` files are excluded from the build context).
- `docker compose up -d --build` builds and runs the production image on port 3000.
- The `Dockerfile` is a 3-stage build (`deps` → `builder` → `runner`) relying on `output: "standalone"` in `next.config.ts` (the default when `NEXT_OUTPUT` is not `export`); the runner stage only copies `.next/standalone`, `.next/static`, and `public`, and runs as a non-root `nextjs` user. If you add a dependency that needs native/runtime files not covered by the standalone trace, the Docker image will be missing them even though `next dev`/`next build` work fine locally.

## Architecture

This is **NutriAI**, a nutrition/diet dashboard. All UI copy is in pt-BR — keep new text consistent with that.

- Next.js App Router (TypeScript, Tailwind CSS v4). Path alias `@/*` → `src/*`.
- Routes: `/login` (sign in / sign up), `/perfil` (body data → calorie goal, plus meals per day — stored in `Profile` but not used anywhere else yet — and `weighInDay`, the weekday (`Date.getDay()`) on which `WeighInReminder` shows on `/` until a weight is logged that day, opening `WeightDialog` right there; first stop after sign-up), `/` (daily goal card + meal plan), `/nutrientes` (macro/vitamin/mineral progress cards), `/alimentos` (foods the user marked "Não gosto / Não quero / Não tenho", grouped by mark, each with its substitute and a "Liberar" button; components in `src/components/foods/`), `/historico` (user weight log — `WeightChart` + `WeightDialog`, entries saved per user via `addWeightEntry` in `auth.ts`; purely a record, it never changes `profile.weightKg` or the calorie target; 7/30/90-day calorie balance, daily intake of one selected nutrient from `/nutrientes` vs its goal (`NutrientChart`, fed by `/history/nutrients` keyed by nutrient `id` and `nutrientGroups` in `src/lib/nutrients.ts`; nutrients with `limit: true` — açúcares, gordura saturada, colesterol, sódio — treat `meta` as a maximum, so the chart text says "limite" and counts days above it), activity data shaped like Google Fit / Apple Saúde exports, past meal plans; components in `src/components/history/`) and `/chat` (AI chat via `/chat/messages`). Page files are thin — they compose `AuthGuard`, the shared `Topbar` and page-specific components.
- **All data comes from the backend; the endpoints are documented in `docs/api.md`** and the request/response types live in `src/lib/api/types.ts` (the contract — keep both in sync). There is no mock data; the old simulated data is in git history (`git show 158453f:src/lib/mock-data.ts`).
  - `src/lib/api/client.ts` — `apiFetch` (base URL `NEXT_PUBLIC_API_URL`, Bearer token from `localStorage` `nutriai:token`, errors as `ApiError` with the body's `error` message; a 401 drops the token).
  - `src/lib/api/query.ts` — `useApiQuery(path)` for reads: in-memory cache per path shared across components, cleared when the token changes. Components render `QueryStatus` (`src/components/api/`) while loading or on error.
  - `src/lib/auth.ts` — session + user state: `POST /auth/login|signup` return a token, then `GET /me` loads a `UserState` (profile, meal times, weights, plan changes, food swaps) read via `useAuth()` (`useSyncExternalStore`; `undefined` on the server, before hydration and while `/me` loads). Every mutation (`saveProfile`, `savePlanChanges`, `markFoodEverywhere`…) sends one request and replaces the state with the full `UserState` the backend returns; failures show a toast rendered by `AuthGuard`. `AuthGuard` (client) redirects to `/login` without a session and to `/perfil` without a profile (`requireProfile={false}` on `/perfil` itself), and shows a retry screen if `/me` fails. Every protected page prerenders as a loading spinner.
  - The backend only provides and stores data: the day's plan math (portions, swaps, redistribution) and the calorie target stay client-side.
- `src/lib/calorie-target.ts` — Mifflin-St Jeor BMR × activity factor, ±goal adjustment (−500 / 0 / +300), floored at 1200 (F) / 1500 (M); plus water (35 ml/kg). The resulting target drives the "Meta diária" card and the history goal line. Macro gram targets come from `/nutrition/today`.
- `src/components/dashboard/`:
  - `Topbar` — client component; shows the app name "NutriAI", nav (`next/link` + `usePathname` for active-route highlighting), the profile link and "Sair". Below `md` the nav is hidden and the pages live in a dropdown menu opened by the hamburger button left of the app name (closes on link click or tapping outside).
  - `MacroDonut` — the "Meta diária" card: a plain-SVG semicircle gauge of kcal consumed vs. the calorie target (consumed = `/nutrition/today` macro grams × `MACRO_STYLE[id].kcalPerGram` from `src/lib/nutrients.ts`, which also holds the macro colors; shown in the arc labeled "kcal consumidas"; full arc when over the target), "Calorias gastas" from the last `/history/activity?days=1` day below it, and the macro `ProgressBar`s + water.
  - `src/components/history/WeightChart`, `BalanceChart`, `NutrientChart` and `ActivityPanel` — Recharts wrappers. **Any component importing from `recharts` must have `"use client"`**, even ones that look presentational (e.g. `StatCard` used to omit it and broke `next build` with `createContext is not a function` during static generation, since Recharts needs client runtime). Set `isAnimationActive={false}` on series (`Area`, `Line`, `Bar`, `Pie`): the entry animation gets stuck after client-side navigation via the navbar and leaves the series clipped to a sliver, even though a full reload (F5) renders fine.
  - `ProgressBar` — shared consumed/target bar, used by `MacroDonut`. `/nutrientes` has three `NutrientSection` cards (Macronutrientes, Micronutrientes split into Vitaminas/Minerais, Fibras) holding one `NutrientTile` per nutrient (`src/components/nutrition/`, data from `/nutrition/today` in `NutrientsOverview`); `nutrientGroups` in `src/lib/nutrients.ts` keeps its own grouping for the history chart.
  - `MealPlan` — loads `/meal-plan`, `/meal-alternatives` and `/foods`, then renders `MealPlanView`. Filter by meal time (each base-plan meal has a `time` like `"12:30"`; the chips are derived from those times, there are no category names). The time badge on each meal opens `TimePickerDialog` (its `TimeFields` is reused by `WeightDialog`) (hour/minute fields that can be typed or stepped with arrows — not `<input type="time">`, whose native Android picker truncates its buttons); the change is saved per user through `saveMealTime` in `auth.ts`, and meals are sorted by time; each meal lists individual foods (amount is always a numeric `grams` field — the backend will send quantities in grams only; household measures like "1 colher de chá" are not used), with per-meal macro/kcal totals computed client-side via `sumTotals`, not stored pre-aggregated.
- Each meal card in `MealPlan` has a remove button that opens `RemoveMealDialog` with three choices: swap for the `/meal-alternatives` entry closest in kcal (same id/time; the card shows no "new suggestion" tag, like created meals), redistribute its kcal to the later meals of the day by scaling their portions up by the same factor, or just remove it. The dialog lists each later meal's kcal before → after for the redistribute option. "Sugerir" and "redistribuir" are day-only (`saveDayPlanChanges`, tagged with the local date and ignored on any other day); "não fazer nada" is permanent (`planChanges.removed` via `savePlanChanges`) — to get a meal back the user creates a new one.
- Plan changes come in two layers in `auth.ts`: `planChanges` (permanent until the user undoes them: removed meals, created meals `added`, `extraFoods`, `scales`) and `dayPlan` (today only: `removed` by redistribute, `replacements`, `scales`). `MealPlan.buildPlan` builds both the permanent plan (base for create/add-food math) and today's view; today's portion factor = permanent × day.
- "Nova refeição" in `MealPlan` opens `CreateMealDialog` (name + time via `TimeFields`); the foods come from the `/meal-alternatives` entry for that time's period (`mealPeriod` in `src/lib/meal-period.ts`: manhã < 11:00, tarde < 17:00, noite), preferring one not already in the plan. The user only gives name + time — the foods are an AI-assistant suggestion, and the card looks exactly like a base-plan meal (no "created by you" tag). Its kcal always come from the other meals of the day: the suggested portion is scaled to at most the day's kcal ÷ number of meals, and every other meal's portions shrink by the same factor. After "Continuar" the dialog shows a confirmation notice with each meal's kcal before → after; nothing is shown as extra rows in the cards.
- Portion changes are factors per meal id (`planChanges.scales` × `dayPlan.scales`, applied with `scaleFoods` to grams + macros). `fitFactor` checks the rounded values the cards will show and tightens the factor so the day's kcal never goes above what it was. Created meals live in `planChanges.added` (ids ≥ 1001) and stay until removed; editing their time updates `planChanges.added` instead of `saveMealTime`.
- The add-food button on each meal card opens `AddFoodDialog`: the user types a food name and clicks "Buscar"; the result is a radio list like `FoodFeedbackDialog` — catalog (`/foods`) foods containing the text (accent/case-insensitive), or, if none, the 5 most similar names (bigram similarity) as suggestions; restricted foods are never listed. The front picks each option's portion (the meal's average kcal per food); every meal's permanent portions shrink so the day total doesn't grow. Stored in `planChanges.extraFoods` at the meal's factor-1 portion, so extras scale with the meal. They stay until removed with the trash button on the food row, which gives their kcal back to all meals.
- `src/lib/food-feedback.ts` — the "Não gosto / Não quero / Não tenho" options (ids, labels, icons), shared by `MealPlan`, `/alimentos` and the history page. Each food row in `MealPlan` has a single "Substituir alimento" button that opens `FoodFeedbackDialog` — like `RemoveMealDialog`, a radio list of the three reasons (each describing where the swap applies) — where the user also picks a substitute from the same catalog group (offered at the same kcal). Two separate things are stored:
  - **Swaps** (what the meals show): "Não gosto"/"Não tenho" → `markFoodEverywhere`, a permanent swap in every meal (`foodSubstitutes`); "Não quero" → `markFoodInMeal`, a permanent swap only in that meal (`mealFoodSwaps`, per user, not per day) — e.g. a food that appears in 3 meals and is marked in one is eaten 2 times a day from then on. `resolveFoods` (from `foodTools(catalog)` in `src/lib/food-substitution.ts`) applies `{...foodSubstitutes, ...mealFoodSwaps[mealId]}`, following chains; `""` means removed without substitute.
  - **Restrictions** (`foodFeedback`, listed on `/alimentos`): restricted foods are never offered as substitutes and the assistant's meal suggestions (new meal / "sugerir uma nova") prefer alternatives without them (`usesRestrictedFood`). "Liberar" (`releaseFood`) only lifts the restriction — **swaps already made stay**; the food does not return to the meals by itself.
- The catalog (`GET /foods`, per-100 g nutrients and a group per food; group labels in `src/lib/food-groups.ts`) — **every food used in a meal must exist in the catalog**, or it can't be substituted.
- `src/components/chat/ChatPanel.tsx` — history from `GET /chat/messages`, suggestions from `/chat/suggestions`; sending posts to `/chat/messages` and appends the assistant's reply.
- `next.config.ts`: `output: "standalone"` is required for the Docker build described above. No external image host is whitelisted (meals have no photos); if you add `next/image` with a remote URL, add its host under `images.remotePatterns` or it will refuse to load.
